# Dependency data

Two sources have different roles. `dependency_sources.py` builds query plans for immutable PyPI distribution metadata. The caller must dry-run and reserve bytes in the existing project-wide BigQuery ledger before executing a plan. `collect_depsdev.py` collects current requirements and resolved graphs through the public deps.dev API; its records never become a historical resolution series.

The default `candidate_history` query discovers distributions that declare any of the 30 target packages, then retrieves all artifact versions of those distributions, including later releases that remove a target requirement. It also retrieves the target distributions themselves. History before January 2023 is retained as a baseline; discovery from all observed history does not make a future declaration count in an earlier week. File-specific variants, requirement strings, extras, environment markers, direct URLs, provider upload times and collection times remain available.

Use `build_dependency_features.py` with a decoded `JSONL.gz` metadata export, registry, query plan, completed-query receipt and a fresh output directory. The receipt must contain `query_sha256`, `job_complete: true`, `all_pages_fetched: true`, `total_rows`, and `output_sha256` for the complete decoded input file. A missing page, changed input or different cohort prevents completion.

For the full metadata export, use `build_dependency_features_streaming.py` with the same arguments. It sorts source rows by canonical distribution through DuckDB, then applies the reference event-time sweep to one distribution at a time. Its weekly output is checked against the full-memory reference implementation. Raw normalized artifacts, parsed declaration edges and every parse error remain compressed and hash-bound. This separate process defaults to one DuckDB thread, a 3 GB query-memory limit, insertion-order preservation disabled, 10 GiB of spill and 100,000 artifact rows per distribution; the disk watchdog preserves a 15 GiB free-space reserve. The ordinary database worker retains its existing 1 GB query-memory setting. Invalid or undated metadata remains visible with affected eligibility disabled.

Artifact format version 2 keeps every original provider field, including the ordered `requires_dist` strings, plus canonical identity, event time and provenance. It avoids duplicating derived `parsed_requirements` arrays inside each artifact. Every derived attribute is retained in `declared_dependency_edges.jsonl.gz` for valid requirements or `parse_errors.jsonl.gz` for invalid requirements, joined by `artifact_id` and `requirement_index`. `reconstruct_requirements` restores the ordered parsed array losslessly. Edges are emitted as they are parsed, and output gzip uses level 3 to limit CPU cost. This changes storage layout rather than collected information; the raw metadata export and completed-query receipt remain unchanged.

Weekly output includes new and cumulative packages declaring a target, declaration-bearing release counts, outbound requirements, and trailing four-week summaries. `dep_latest_uploaded_release_declaring_packages` explicitly uses each package's latest uploaded release; it does not measure users or the version selected by pip. Conditional and optional requirements remain labeled. Provider upload events support retrospective reconstruction, while historical retrieval vintages remain unavailable. Parse errors and unknown dates remain visible and disable affected eligibility rather than becoming zero.

`run_metadata_backfill.py` publishes the validated source through `data/full_scope/dependency_history`, an atomic pointer to an immutable run. After graph construction, `audit_dependency_conflicts.py` compares every conflicting file identity, and `review_dependency_conflicts.py` resolves cohort-feature uncertainty using the complete artifact context of affected downstream packages. Changes only to descriptions, markers or version constraints do not change inbound membership counts. Reliable other files can remove an apparent ambiguity. Uncertain first-declaration dates, latest-release declarations and four-week effects disable the affected inbound eligibility flag; the exact metric/week reasons stay in `conflict_feature_review.json`. All original artifact, edge and error files remain unchanged, and numeric observations remain available for diagnostics. Repeated finalization selects the reviewed source rather than rolling back its masks.

`collection_complete` and `input_query_complete` mean the full hash-bound query was retrieved, every artifact was processed and the frozen cohort matches. They are separate from `quality_status`: the current full capture remains `needs_review` because provider metadata contains malformed requirements and conflicting claims. As of the initial 2026-11-03 capture, 3,093,989 retrieved rows yield 3,079,014 distinct artifact records and 73,866,993 valid declaration edges. The 6,000 complete tool/week rows span 2023-01-02 through 2026-10-26; earlier artifacts supply the pre-study baseline. A complete capture does not make every feature scientifically eligible or establish historical retrieval vintages.

Current deps.dev collection supports safe resume in the same output directory, at most 150 requests per invocation, one second between requests, immutable gzip response bodies and checksums, explicit 400/404 source gaps, provider cooldowns and a 15 GiB free-space guard. All 30 tools require at most 120 successful requests for package metadata, chosen-version metadata, requirements and resolved graphs. Fresh observations belong in new dated directories.

`build_download_dimension_features.py` validates completed rich download exports and creates daily totals, full Monday–Sunday weekly features and long dimension-composition Parquet files. The dimensions are package version, Python version/implementation, OS, installer, country, artifact type, reported CI and HTTP status. Version diversity, top-version share and composition entropy describe artifact request counts; reported CI values do not identify human users. Unknown category values stay explicit. When verified immutable artifact history is available, recent-version uptake is the share of requests to versions first uploaded in the previous 28 days; missing release dates remain unknown and the share is a lower bound.

Pass `--query-root`, `--registry`, `--primary-snapshot`, `--output`, and `--end-exclusive`, with optional `--dependency-history`. Every source interval needs a complete receipt and matching bytes, query parameters and cohort. The newest successful whole interval wins when a pilot and historical query overlap, including an empty replacement. The builder preserves the full requested tool/day grid and pre-artifact nulls, reports missing intervals, and compares new totals with the hash-verified frozen primary dataset. Differences are retained in `frozen_primary_differences.csv`; they never replace the primary target or promote a model. A pilot-only build remains `partial`. The two-day feature-availability lag is explicitly an assumption.

Run tests with a Python environment containing `packaging`:

```sh
python -m unittest discover -s . -p 'tests_*.py' -v
```
